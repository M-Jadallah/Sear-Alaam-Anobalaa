# النشر على Coolify — VPS بذاكرة 2GB

الرابط المعتمد: https://sear-alaam-anobalaa.jadallah.work

## مسار الإصدار

`main` هو مصدر الشيفرة. يبني GitHub Actions الواجهة والنماذج والفهرسين وصور Linux/AMD64، ويفحص الحاويات بقيود الإنتاج. بعد نجاح الاختبارات فقط ينشر صور GHCR الخاصة وينشئ تحديثًا متقدمًا لفرع `production`، وفيه `docker-compose.yml` ببصمات صور ثابتة و`deploy/release.json` بتقرير الإصدار. ملف Compose على `main` يحتوي علامة `unreleased` عمدًا؛ لا تنشر فرع main.

تعتمد عملية البناء على حصة GitHub Actions والتخزين المتاحين للحساب. لا يستعمل التطبيق أي API مدفوعة أو مفتاح استدلال. إعداد النماذج والفهرسة الأول طويل، وله ذاكرة مخبأة بحسب بصمات المدخلات. فشل البناء أو التقييم يمنع تحديث فرع الإنتاج.

## إعداد أول مرة

1. تحقق من أن سجل A للدومين يشير إلى VPS، وأزل أي سجل AAAA لا يشير إلى IPv6 عامل. يجب أن يصل المنفذان 80 و443 إلى Traefik. إعداد Coolify المفترض هو شبكة `coolify`، ومدخلا `http` و`https`، ومحلل شهادات `letsencrypt`.
2. انتظر نجاح workflow وظهور فرع `production`. اربط المستودع الخاص `M-Jadallah/Sear-Alaam-Anobalaa` عبر GitHub App، واختر الفرع `production`.
3. اختر Docker Compose، وBase Directory يساوي `/`، وموقع الملف `/docker-compose.yml`. فعّل **Raw Compose / deploy file as-is**. لا تضف دومينًا ثانيًا في شاشة Domains؛ ملصقات Traefik مضمنة في الملف. لا تفعّل معاينات PR لهذه الحزمة ذات التخزين والدومين الثابتين.
4. في **Servers → السيرفر → Registries** سجّل الدخول إلى `ghcr.io` باسم حساب يملك صلاحية الصور، وبرمز PAT classic بصلاحية `read:packages` فقط. إذن قراءة Git لا يغني عن إذن سجل الصور.
5. أضف متغيري التشغيل `SIYAR_ADMIN_USERNAME` و`SIYAR_ADMIN_PASSWORD`؛ كلمة المرور 14 حرفًا على الأقل. لا تضعهما في Git أو ملف Compose أو لقطات السجل.
6. فعّل Auto Deploy لفرع production وانشره. تهيئ خدمة init البيانات ثم تبدأ API والواجهة والنسخ. افتح `/api/ready` ثم `/api/semantic/status`؛ الجاهزية الدلالية تشمل الفهرسين. ادخل من `/login`.

تغيير كلمة مرور المدير في Coolify وإعادة تشغيل API يحدث التجزئة ويلغي الجلسات السابقة. مدة الجلسة ثماني ساعات. تُسجل قرارات المراجعة باسم الحساب المصادق عليه، مهما كان الاسم المرسل في جسم الطلب.

مراجع: [Compose وRaw mode](https://coolify.io/docs/applications/builds/docker-compose)، [Traefik](https://coolify.io/docs/core/networking/proxy/traefik/overview)، [صلاحيات GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

## البيانات والحدود التشغيلية

المصدر محفوظ حرفيًا وبصمته `7ae7f691ffe236f5b888f5dfdf18becd9e5ea17ab6b5851528db5efd333886c0`. الحزمة الأولية في `deploy/seed` لقطة SQLite متسقة، مضغوطة ومقسمة إلى أجزاء 20MiB، ومعها بصمات الصفوف والأجزاء. تتضمن 5943 ترجمة و129006 مقاطع وأربع دفعات منشورة و10 سجلات لتاريخ تصحيح القراءة. سجلات التأليف والاختبارات في reference لا تعني اعتمادًا بشريًا.

التهيئة تفك الحزمة إلى وحدة `siyar-library-data` مرة واحدة. القاعدة الموجودة لا تستبدل عند التحديث ولو احتوت مراجعات أحدث من الحزمة. تجري نسخة قبل تهيئة المخطط في عمليات النشر التالية. وحدة `siyar-library-backups` مستقلة. حذف التطبيق مع اختيار حذف وحدات التخزين، أو `docker compose down -v`، يحذف البيانات؛ أمر down العادي لا يحذفها.

النماذج والفهارس ملفات ثابتة داخل صورة API، ولا تُنزل أثناء البحث. تغيير حدود المقاطع بالمراجعة قد يجعل فهرس الفقرات قديمًا؛ تعرض الواجهة حالته ولا تدعي جاهزيته. لإعادة بنائه صدّر نسخة متسقة حديثة من الإنتاج، وابنِ منها حزمة إصدار جديدة خارج VPS. لا تستبدل قاعدة السيرفر بحزمة أقدم؛ تحقق من تطابق بصمة المصدر ومراجعة التقسيم قبل اعتماد الفهرس الجديد. تجري ترحيلات المحتوى مستقلّة مع حفظ سجلات المراجعات.

الميزانية: API وعامل الاستدلال معًا 1024MiB، والواجهة 64MiB، والنسخ 96MiB. عامل استدلال واحد وخيط CPU واحد، مع ثلاثة طلبات منتظرة؛ الطلب الخامس يرفض بـ429، والمهلة 60 ثانية. التخزين المؤقت 64 استعلامًا لمدة 15 دقيقة. تُحد قراءة SQLite المتزامنة بمعالجين، والاتصالات المتزامنة بـ16، لأن قراءة المصدر تجلب نصه إلى الذاكرة. توجد حدود إضافية لمحاولات الدخول والبحث والقراءة العامة في nginx. افحص الاستخدام الفعلي لـCoolify والتطبيقات الأخرى؛ لا تساوي حدود الحاويات ضمانًا لتوفر الذاكرة على المضيف.

## النسخ والاستعادة والرجوع

تبدأ نسخة يومية بعد جاهزية API ثم تتكرر كل 24 ساعة. تُضغط لقطة SQLite Backup API؛ الاحتفاظ بثلاث يومية وواحدة قبل المهاجرة لكل قاعدة. تحفظ جلسات المدير في `auth.sqlite3` مستقلًا. هذه نسخ على نفس VPS؛ تعطل القرص الكامل يحتاج نسخة خارجية لا تشملها هذه الحزمة.

في Terminal خدمة backup لنسخة فورية:

```sh
python -m backend.deployment backup --folder /backups
```

للتحقق من نسخة مستعادة إلى ملف جديد، دون استبدال القاعدة الحية:

```sh
python -m backend.deployment restore --archive /backups/library-daily-TIMESTAMP.sqlite3.gz --db /backups/restored.sqlite3
python -m backend.deployment verify --db /backups/restored.sqlite3
```

استعادة الإنتاج إجراء صيانة: أوقف API وbackup، احتفظ بالقاعدة الحالية وملفي WAL وSHM بعد الإيقاف، تحقق من النسخة المستعادة ثم ثبّتها بصلاحيات UID/GID 10001 وأعد التشغيل. لا تنسخ SQLite وحده أثناء الكتابة في WAL. استعادة auth القديمة تعيد بيانات جلساتها؛ أبطل الجلسات بتغيير كلمة المدير بعد الاستعادة.

للرجوع البرمجي انشر commit الإصدار السابق من `production` عبر Coolify. يبقى التخزين الحالي والمراجعات محفوظين. ترحيلات النشر التلقائي إضافية ومتوافقة؛ الترحيل الهدام يحتاج صيانة منفصلة. لا تعد باستمرار الخدمة دون انقطاع خلال إعادة إنشاء حاويات Compose.

احتفظ بصورة الإصدار الحالي والسابق فقط بعد التأكد من نشر الجديد. تنظيف صور VPS يتم بمعرفات صور هذا التطبيق وحدها بعد فحص `docker image ls` ومقارنتها ببصمتي الإصدارين. لا تستخدم `docker system prune` أو تنظيفًا شاملًا على سيرفر يستضيف تطبيقات أخرى. قبل التحديث افحص `df -h` وتأكد أن مساحة سحب الجديد والنسخة المضغوطة متاحة مع بقاء 2GiB فارغة؛ قد تحتاج حذف إصدارات هذا التطبيق الأقدم فقط.

## الاختبار وما لا يقاس عن بعد

تشغيل محلي:

```sh
python -m pytest -q
npm --prefix frontend ci
npm --prefix frontend run build
npm --prefix frontend run test:e2e -- production-auth.spec.ts
```

Browser plugin غير متاح في جلسة التنفيذ؛ اختبار الواجهة يستخدم Playwright وHTTPS على قاعدة مؤقتة. لا يكتب الاختبار إلى مكتبة المستخدم. يختبر CI أيضًا حاويات فعلية بلا اتصال خارجي من API، وحدود الذاكرة، والشواهد، والدخول، وإعادة الإنشاء، والنسخ والاستعادة. ملفات الأدلة في artifact باسم deployment-verification.

اختبار VPS النهائي يحتاج صلاحية وصول إليه: قياس OOM وإعادة التشغيل، وp95 الدافئ ≤30 ثانية، وهامش RAM لا يقل عن 200MiB، وHTTPS الفعلي، ثم إعادة تشغيل VPS والرجوع لإصدار سابق. لا يُعلن اكتمال هذا القياس من نجاح CI وحده.
